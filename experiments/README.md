# ktru-autofill

Автозаполнение характеристик КТРУ по тексту позиции («Путь А: эмбеддинги по фрагментам»).

```
Вход:  "бумага для принтера А4 80 грамм 500 листов белая" + кандидаты КТРУ (шаг 2)
Выход: {"Формат": "A4", "Плотность": {"значение": 80, "единица_как_написано": "грамм"},
        "Количество листов в пачке": 500, "Цвет": "Белый", "Класс бумаги": null, ...}
```

## Запуск

```bash
uv sync --all-extras                      # с моделью эмбеддингов (CPU torch)
uv run ktru-autofill -c data-archived/candidates_paper.json "бумага для принтера А4 80 грамм 500 листов белая"
uv run ktru-autofill -c data-archived/candidates_paper.json -d "бумвга А4 для лазерного принтера"   # + фрагменты, методы, опечатки
uv run ktru-autofill -c data-archived/candidates_paper.json --no-embeddings < positions.txt          # только rapidfuzz, по строке из stdin
uv run uvicorn ktru_autofill.api:app      # POST /fill {"text": ..., "candidates": [...], "details": false}
uv run pytest
```

Модель: `intfloat/multilingual-e5-small` (меняется через `KTRU_EMBED_MODEL`). Если extra `embeddings`
не установлен или задан `KTRU_NO_EMBEDDINGS=1`, работает только нечёткое сравнение.

## Формат кандидатов

```json
[{"code": "17.12.14.129-00000001", "name": "Бумага для офисной техники белая",
  "characteristics": [
    {"name": "Формат", "type": "enum", "values": ["A3", "A4"]},
    {"name": "Плотность", "type": "number", "unit": "г/м2", "unit_aliases": ["г", "гр", "грамм"], "range": [40, 300]},
    {"name": "Количество листов в пачке", "type": "count", "unit": "лист", "unit_aliases": ["л"]}]}]
```

`enum` — выбор из значений; `number` — в ответе `{"значение", "единица_как_написано"}`; `count` — просто число.
Характеристики нескольких кандидатов объединяются по имени в одну анкету (шаг 3.1).

## Как работает (`src/ktru_autofill/autofill.py`)

1. **Числа** (`numbers.py`): регулярка вытаскивает «число + единица» («80 грамм», «80г/м²», «500л»).
   Единица → характеристика по `unit`/`unit_aliases`. Число без единицы назначается по слову перед ним
   («плотность 80») или по `range`, если подходит ровно одна характеристика. Выход за диапазон — предупреждение.
2. **Текст** (`text.py`): токены → леммы pymorphy3 → без стоп-слов. Кириллица в кодах латинизируется («А4» → «a4»,
   «класс С» → «c»).
3. **Опечатки**: слово, которого нет в словаре pymorphy3, сверяется rapidfuzz со словами названий и значений
   кандидатов: «бумвга» → «бумага» (0.83). Исправление попадает в `опечатки` — материал для шага 6.
4. **N-граммы 1–3** сравниваются только со значениями анкеты:
   точное совпадение лемм → 1.0; rapidfuzz ≥ 0.80; косинус эмбеддингов ≥ 0.88.
   Значения с цифрами и короткие коды («A4», «C») — только точно.
   Для векторов дополнительно требуется *контраст* ≥ 0.06 над средним сходством фрагмента со всей анкетой и
   отрыв ≥ 0.02 от соседнего значения той же характеристики: на коротких фразах косинусы сжаты в 0.8–0.9,
   и один порог даёт ложные срабатывания («бумага» ~ «белый» = 0.82).
5. **Распределение**: жадно по убыванию оценки; каждая характеристика и каждый кусок текста используются один раз.
   Не найдено → `null`.

Пороги — параметры `Autofiller(...)`.

## Оценка качества (`src/ktru_autofill/evaluate.py`)

Берутся СТЕ с уже заполненными характеристиками; по описанию прогоняется извлечение и сравнивается с эталоном.

```bash
uv sync --all-extras
uv run ktru-eval путь/к/ste.xlsx -c анкеты_ктру.json --errors errors.jsonl --json metrics.json
uv run ktru-eval путь/к/ste.csv --text-col "Наименование СТЕ" --chars-col "Характеристики" --code-col "Код КТРУ" --limit 2000
```

- **Точность** = верных извлечённых / всех извлечённых (значение для характеристики, которой нет в эталоне, — ошибка).
- **Полнота** = верных извлечённых / всех характеристик эталона.
- **«Встречается в описании»** — доля характеристик, чьё значение вообще есть в тексте: это потолок полноты
  для извлечения из текста. Остальное (например, класс бумаги, которого нет в названии) найти нельзя.
- Разбивка по методам (точное / нечёткое / вектор / число+единица …) и по характеристикам; ошибки — в `--errors`.

Форматы: `.jsonl/.json/.csv/.xlsx/.parquet`. Характеристики — dict, список `{name, value, unit}`,
JSON-строка или «Имя: значение; Имя: значение». Колонки угадываются по типичным названиям, иначе `--*-col`.

Анкета: из `-c` по коду КТРУ СТЕ (шаг 2 считается идеальным). Без `-c` она строится из самого датасета —
все значения, встреченные у СТЕ с тем же кодом; единиц там меньше, чем в настоящем КТРУ, поэтому числа
чаще назначаются по диапазону, а не по единице.

`data-archived/sample_ste.jsonl` — 10 придуманных СТЕ для проверки стенда, не замер качества.

## Настоящий КТРУ и дерево ОКПД2 (`src/ktru_autofill/hierarchy.py`)

Данные (не в git, скачиваются один раз):

```bash
mkdir -p data-archived/raw
curl -sL -o data-archived/raw/okpd2.json https://raw.githubusercontent.com/prog815/okpd2/main/okpd2.json   # ОКПД2, Росстат, 21 102 узла
curl -sL -o data-archived/raw/ktru.json https://huggingface.co/datasets/Meln1kz/KTRU_Codes/resolve/main/ktru.json  # 21 635 позиций КТРУ
uv run python -m ktru_autofill.ktru_import data-archived/raw/ktru.json data-archived/ktru_real.json
uv run ktru-autofill --real "бумага для принтера А4 80 грамм 500 листов"
```

Выгрузка КТРУ неполная (половина — реагенты ИВД и услуги): бумага, школьная мебель, техника есть,
шприцев, ручек, масок нет.

Конвейер на настоящем КТРУ: **дерево ОКПД2 → товар → анкета → характеристики → код**.

1. Товар ищется beam search по дереву ОКПД2 (класс → подкласс → … → категория → позиции КТРУ).
   Узел оценивается эмбеддингом `multilingual-e5-small`: сходство запроса с лучшим названием
   позиции КТРУ в поддереве (и, с весом α, с названием узла ОКПД2). Числа и единицы из запроса
   убираются — «монитор 27" IPS» ищется как «монитор IPS».
2. Внутри выбранных кодов остаются позиции с самыми похожими названиями.
3. Характеристики сужают коды. Позицию отбрасывает только противоречие (характеристика есть,
   значение не подходит): в КТРУ наборы характеристик разные даже у позиций с одним названием.
   Значение, которое не принимает ни одна позиция, не применяется (предупреждение).
   В конце остаются позиции с наибольшим числом совпавших характеристик.
   Слабые совпадения (вектор, нечёткое, по диапазону) не сужают.

### Сравнение способов найти товар (`experiments/retrieval_eval.py`)

97 запросов «как пишет заказчик» к реальному КТРУ (`data-archived/test_real_retrieval.jsonl`, эталон — допустимые
названия позиций). Параметры подбирались на этих же запросах — цифры слегка оптимистичны для всех.

| способ | товар найден | на 1-м месте | позиций остаётся (медиана) | время |
|---|---|---|---|---|
| плоский: ближайшие названия КТРУ | 97.9% | 91.8% | 9 | 150 мс |
| дерево, softmax в узле + среднее геометрическое (как в TypeSafe cookbook) | 87.6% | 86.6% | 5 | 8 мс |
| **дерево, сырые оценки узлов** (по умолчанию) | **95.9%** | **91.8%** | **6** | **7 мс** |
| снизу вверх: названия голосуют за группу ОКПД2 | 90.7–92.8% | 89.7–90.7% | 5–7 | 15 мс |

- Softmax в каждом узле даёт перекос: узел с двумя детьми получает рёбра ≈ 1, а «26 Компьютеры»
  с десятками детей — размазанные, и верный путь проигрывает по среднему геометрическому. Сырые
  оценки этот перекос убирают.
- С эмбеддингами дерево почти не точнее плоского поиска, но сужает сильнее, в 20 раз быстрее
  и показывает объяснимый путь по ОКПД2. С моделью, которая сравнивает варианты между собой
  (Jev / Laya Choice), выигрыш дерева может быть больше — оценщик подключается без изменения поиска.
- Оставшиеся промахи — пределы эмбеддингов: сокращения («ИБП», «скотч»), «АИ-92» против «Б-92».
  Их закрывает словарь синонимов, а не алгоритм поиска.

## Замер качества и артефакты

```bash
uv run ktru-eval data-archived/test_handwritten.jsonl data-archived/test_generated.jsonl            # синтетический каталог
uv run ktru-eval data-archived/test_generated.jsonl --strip-synonyms                       # незнакомые формулировки
uv run ktru-eval data-archived/test_real_retrieval.jsonl --real                            # настоящий КТРУ: найден ли товар
uv run ktru-eval ste_организаторов.xlsx --real --text-col ... --chars-col ...     # датасет организаторов
uv run pytest                                                                     # + артефакт в reports/pytest/
```

Каждый прогон сохраняет `reports/<дата-время>/<набор>/`:
`report.md` (сводка, все выдуманные и неверные значения, товар найдено vs ожидалось),
`metrics.json`, `items.jsonl` (по каждой СТЕ: товар, код, сужение, каждая характеристика со статусом),
`values.csv` (то же таблицей для Excel, разделитель «;»).

- **точность** — верных среди извлечённых; **полнота** — найдено из эталона;
- **выдумано** — извлечено, неверно и не подтверждается текстом (ни слов значения или его синонима,
  ни такого числа нет). Считается отдельно: для госзакупок это худшая ошибка;
- статус каждого значения: верно / неверно (из текста, но не то) / выдумано / лишнее / пропуск /
  нет в тексте / подсказка верна|неверна.

Выдумки давали эмбеддинги: «кожзам» → «Натуральная кожа», «без замка» → «Без дверей». Поэтому
вектор с косинусом ≥ 0.94 заполняет значение, а 0.88–0.94 — только **подсказка** на подтверждение
(в `подсказки` ответа, в характеристики не пишется). Нечёткое сравнение принимает значение, только
если у каждого его слова есть пара в тексте. Порог 0.94 подобран на этих же наборах — на данных
организаторов его нужно перепроверить.

Результаты (`reports/20261008-210432`):

| набор | точность | полнота | выдумано | подсказки (верных) | товар первым |
|---|---|---|---|---|---|
| ручной, 70 СТЕ | 100% | 99.5% | 0 из 212 | 3 (0) | 98.6% |
| сгенерированный, 500 СТЕ | 99.4% | 79.8% (потолок 78.8%*) | 0 из 1436 | 30 (5) | 99.4% |
| сгенерированный без синонимов | 98.5% | 60.6% | 0 из 1100 | 100 (67) | 99.4% |
| настоящий КТРУ, 97 запросов | — | — | 2 из 71 не подтверждены текстом | 17 | 91.8% |

\* полнота выше «потолка», потому что значения вроде «регулируемый» → «Да» эвристика упоминания не всегда видит.

### Laya-multilingual без дообучения (`experiments/laya_eval.py`)

`uv sync --extra laya`; вопрос на характеристику — Choice «какое значение указано», варианты: эталон,
7 частых значений категории и «не указано». 200 тестовых СТЕ, 971 пара (`reports/tenderhack-20261008/laya/`):

| | Laya: эталон | Laya: другое значение | система: эталон | система: другое значение |
|---|---|---|---|---|
| значение есть в тексте (155) | 58.7 % | 32.3 % | 58.1 % | 8.4 % |
| значения нет в тексте (816) | 32.6 % | 27.3 % | 0 % | 3.7 % |

Сама по себе Laya не годится для заполнения: верных столько же, сколько у системы, а неверных в 4–7 раз

вопросы одним проходом), 2.4 ГБ памяти на CPU.

### Jev: числа с исходным контекстом (`experiments/ste_to_jev.py`)

Схема вопросов берётся из КПГЗ, вход — название и описание реальной карточки СТЕ; заполненные
характеристики используются только для сверки. Для чисел Jev выбирает кандидат из текста,
перевод единиц и проверку диапазонов выполняет код. Каждый кандидат сопровождается исходными
фрагментами всех его вхождений; для составных размеров указывается позиция числа в записи,
но не предполагаемая характеристика. Модель должна использовать связь в тексте и явные подписи
(например, Ш×Г×В), а при неоднозначности выбирать «не указано». Подсказки порядка размеров по
категории удалены из кода; `data/dim_order.json` больше не используется. Отдельно считаются доля
выданных ответов и точность среди них: отказ от угадывания не равнозначен неверному значению.

Предыдущий эксперимент с порядком по категории (отклонён): на 100 СТЕ, 232 неподписанных размерах
(seed 0) без подсказок с карточкой
совпали 154 значения (66.4%), с подсказками — 161 (69.4%). Подсказка была доступна для 133 размеров;
32 ответа исправились, 25 правильных стали ошибочными. Это небольшой прирост, не основание
автоматически заполнять неоднозначные размеры. Выборка отобрана по наличию сопоставимого эталона;
результат не является оценкой на всех СТЕ. Неподписанные размеры считаются отдельно от извлечения
однозначно подтверждённых текстом значений.

```bash
uv run python experiments/ste_to_jev.py --sample 100 --focus dims --log-dir reports/ste_jev_context_dims
uv run python experiments/ste_to_jev.py --compare reports/ste_jev_focus_base/eval_dims_n100_seed0.json reports/ste_jev_context_dims/eval_dims_n100_seed0.json
```

СТЕ проверяются параллельно: по умолчанию 8 работников, число задаётся `--workers N`.
Порядок итоговых результатов совпадает с выборкой независимо от порядка завершения запросов.
Внутри каждой СТЕ вопросы отправляются пакетами по четыре, чтобы не превысить лимит токенов API.
Ответы кешируются по полному запросу. `--compare` не вызывает API, проверяет совпадение выборок,
вопросов и эталонов и сохраняет парные изменения ответов. Старые результаты эксперимента с
подсказками сохранены в `reports/ste_jev_focus_hints/compare_eval_dims_n100_seed0.json`.

`--search-category` в `ste_to_jev.py` и `kpgz_to_jev.py` заменяет готовый КПГЗ векторным поиском
`google/embeddinggemma-2` по тексту товара. Индексируются только категории со схемами: название,
путь предков и названия характеристик. Нормированные векторы сравниваются по косинусу;
вопросы строятся по top-1, top-5 и scores сохраняются в логе (`--category-top-k N`). Категория
карточки не передаётся ни поиску, ни Jev; её код остаётся только эталоном для метрик top-1/top-k.
Выборка `--sample` по-прежнему отбирается по доступному эталону, не представляет все СТЕ.
Индекс кешируется в `data/cache/kpgz_embeddinggemma.npz`; при изменении каталога или параметров
эмбеддингов перестраивается. Для запроса и документов используются разные поисковые префиксы модели.

```bash
uv run --extra embeddings python experiments/kpgz_to_jev.py --search-category --text "Бумага офисная А4 80 г/м2, 500 листов" --call
uv run --extra embeddings python experiments/ste_to_jev.py 1160210 --search-category --log-dir reports/ste_jev_search
```

На `inh-compute` проект находится в `~/workspace/hack`. Там используется готовое CUDA-окружение
`.venv`; `uv sync` с текущим CPU-индексом проекта заменит GPU-версию PyTorch. Запуск на сервере:

```bash
ssh inh-compute 'cd ~/workspace/hack && .venv/bin/python experiments/ste_to_jev.py --sample 100 --search-category --embedding-device cuda --workers 8 --log-dir reports/ste_jev_search'
```

На V100 EmbeddingGemma запускается в float32, на GPU с native bf16 — в bfloat16.

#### Категория по соседям-СТЕ и выбор Jev

`--category-neighbors <ste-details.jsonl.gz>` (вместе с `--search-category`) берёт категорию не по
ближайшей схеме, а голосованием `--neighbors-k` (5) ближайших карточек СТЕ: вес соседа
exp((cos − cos_max) / 0,05). Корпус — до 20 карточек на КПГЗ, лимит 20 000, отбор по хешу ID;

`data/cache/ste_neighbors_embeddinggemma.npz`.

#### Сравнение алгоритмов (`experiments/cluster_benchmark.py`, `experiments/cluster_robust.py`)
